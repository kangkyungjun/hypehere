## 1. ① 제한 분석 종목 — 지금 **잘못된 숫자를 보여주고 있다**

### 현재 동작

```dart
// lib/screens/ticker_detail/widgets/ticker_insight_section.dart:72
final probability = latestData.aiProbability ?? 0.5;
final isUptrend = probability >= 0.5;
final confidencePercent = (probability * 100).toStringAsFixed(0);
```

`limited` 종목은 서버가 `probability: 0.5`를 보낸다. 앱은 그걸 그대로 받아
**"AI 상승 확률 50%" + 상승 아이콘(`isUptrend = 0.5 >= 0.5`)** 으로 그린다.

스펙이 경고한 그대로다. 게다가 `?? 0.5` 폴백 때문에 **값이 아예 없어도**
같은 화면이 나온다 — 즉 "데이터 없음"과 "50%"가 구분되지 않는다.

지금 FDXF·HONA·SPCX 세 종목이 이 상태다.

### 조치

1. **`data_quality` 모델 추가.** `analysis_mode` · `history_days` ·
   `ai_available`. **필드가 없으면 `full`로 간주**(과거 데이터 호환, 스펙 명시).
2. `limited`면 **AI 확률 블록 전체를 렌더하지 않는다.** 숫자를 숨기는 게
   아니라 블록을 빼야 한다 — 빈 게이지만 남으면 "0%"로 더 오해된다.
3. 그 자리에 **"제한 분석" 안내**를 넣는다. 서버가 `summary` 앞에 붙여주는
   5개국어 안내문이 이미 있으므로, 앱은 **배지 + 한 줄 설명**만 담당한다.
4. **점수 옆 배지**: `신규상장` (`limited`의 사용자 언어). "제한 분석"은
   내부 용어라 사용자에게는 이유를 쓰는 편이 낫다 —
   `상장 N일` 형태로 `history_days`를 쓴다.
5. `?? 0.5` 폴백 제거. 값이 없으면 `full`이라도 블록을 숨긴다.

### 랭킹·추천 포함 여부 — **제외를 권고**

추천 로직은 `score ≥ 65` 필터 + `0.7×점수 + 0.3×모멘텀`이다
(`recommendation_grid.dart`의 `compute`). `limited`는 점수 실질 범위가
17~83이라 상단이 잘려 **구조적으로 추천에 덜 뽑히지만 아예 안 뽑히진
않는다.** AI 예측이 빠진 종목을 "AI 추천"으로 올리면 신뢰를 깎는다.

→ `recommendation_grid.compute`와 랭킹에서 `analysis_mode == 'limited'`를
**제외**한다. 검색·보유·관심종목에서는 정상 노출한다.

## 2. ② EXTRA 종목 — 확인 결과 **이미 안전하다**

스펙이 우려한 "지수별 종목 수(500/100/30) 하드코딩"을 전수 검색했다:

```
lib/screens/ai_lens/ai_lens_screen.dart:808-810   ('SP500','S&P') ('NASDAQ100',…) ('DOW30',…)
lib/screens/dashboard/sector_overview_screen.dart:38-40  동일
```

**지수 코드와 라벨만 있고 개수는 어디에도 없다.** 필터는 서버에 코드를
넘겨 받아오는 구조라 503/101/30으로 바뀌어도 영향이 없다.

EXTRA는 지수 필터 칩에 없으므로 지수 탭에서 자연히 빠진다. 검색·보유·
관심종목은 티커 기반이라 그대로 노출된다. **코드 변경 불필요.**

> 다만 회귀를 막기 위해 "지수별 종목 수를 하드코딩하지 않는다"는 계약을
> 테스트로 남긴다(숫자 500/100/30이 지수 코드 근처에 나타나면 실패).

## 3. ③ 갱신 중단 종목 — 날짜는 있고 배지가 없다

### 현재 동작

```dart
// lib/screens/ticker_detail/widgets/ticker_header_widget.dart:186
'${l10n.updatedDate} ${latestData.date.toString().split(' ')[0]}'
```

기준일은 **이미 표시된다.** 스펙 요청의 절반은 충족돼 있다.

### 조치

`최신 거래일 - item.date >= 5 거래일`이면 **`업데이트 중단` 배지**를 단다.

**누가 판정할지가 문제다.** 앱은 "최신 거래일"을 모른다. 두 안:

| 안 | 내용 | 평가 |
|---|---|---|
| **A** | 서버가 `stale: true`를 내려준다 | **권고.** 서버는 전 종목의 최신일을 안다 |
| B | 앱이 다른 종목(예: 지수)의 date와 비교 | 비교 대상이 같이 늦으면 오판(⑧ 참조) |

**A를 요청한다.** 스펙의 "(선택) stale 판정"을 **필수로 올려 달라.**
B는 ⑧("종목마다 날짜가 다를 수 있다")과 정면으로 충돌한다 — 10/1처럼
공급원 장애로 일부만 하루 늦으면 멀쩡한 종목에 "상장폐지" 배지가 붙는다.
그건 지금 상태보다 나쁘다.

서버 `stale`이 오기 전까지는 **배지를 달지 않는다.** 기준일 표시만으로도
사용자는 "오래된 데이터"를 읽을 수 있다.

## 4. ④ 종목명 대체 — 티커 상세는 **이미 맞다**

```dart
// lib/screens/ticker_detail/ticker_detail_screen.dart:309
_tickerInfo != null
    ? (isKo && _tickerInfo!.nameKo != null
        ? _tickerInfo!.nameKo!
        : _tickerInfo!.name ?? ticker)   // ← name_ko → name_en → ticker
    : ticker
```

`earnings_data.dart:44`도 `nameKo ?? nameEn ?? ticker`로 맞다.

### ⚠️ 다만 BE 이슈의 원인 진단은 서로 다르다

스펙은 "지난번 BE 종목 이슈의 원인이 이것(name_ko null)"이라고 적었다.
앱 쪽에서 본 원인은 **다른 것**이었다:

```dart
// 개편 전 ticker_detail_screen
Future.wait([getChartData(...), getTickerInfo(...)])
```

`getTickerInfo`가 404면 `Future.wait`이 **차트까지 버려서** 화면 전체가
에러로 떨어졌다. 이름이 null인 문제가 아니라 **조회 자체가 실패**했다.

이건 2026-09-30에 고쳤다(커밋 `6e0ba88`). 기업정보 실패를 삼키고 차트만으로
화면을 세운다. 이름은 `ticker`로 폴백된다.

→ **두 원인이 겹쳤을 가능성이 높다.** 서버에서 BE의 `name_ko`를 채워주시면
표시명이 완성되고, 앱은 이미 실패해도 안 죽는다.

### 추가 점검 결과 — 남은 구멍 없음

`ticker_info.dart:36`의 `displayName`이 `name ?? ticker`로 `nameKo`를
건너뛰길래 호출부를 확인했다. 쓰는 곳은 `community_feed_screen.dart:1005`
한 곳이고, 거기서는 **`nameKo`를 따로 덧붙여** `Apple Inc. / 애플` 형태로
쓴다. 의도된 동작이다.

→ **앱 쪽 ④ 작업 없음.** 서버가 `name_ko`만 채워주면 된다(S4).

## 5. ⑤ 클래스주 티커 — **클라이언트 정규화가 없다**

검색은 서버에 그대로 넘긴다:

```dart
// lib/services/analytics_api_client.dart:393
Future<List<TickerInfo>> searchTickers(String query) async {
  ...Uri.parse('$_baseUrl/api/v1/tickers/search')
```

사용자가 `BRK.B`나 `BRKB`로 치면 서버가 어떻게 처리하는지에 달려 있다.

### 조치

**양쪽 다 한다.**
- 앱: 쿼리에서 `.`·`-`·공백을 제거해 **원본과 정규화본 둘 다** 비교하도록
  로컬 필터를 보강한다(서버 결과를 받은 뒤 재정렬·보강).
- 서버: 같은 정규화를 적용해 달라. 앱만 하면 서버가 `BRK.B`를 못 찾을 때
  결과가 비어 앱이 보강할 것도 없다.

**서버 쪽이 더 중요하다** — 검색은 서버가 후보를 주지 않으면 앱이 할 수 있는
게 없다.

## 6. ⑥ 데이터 없는 종목 — **지난주 이미 구현했다**

스펙 요청: *"404나 빈 값이면 오류 화면 대신 '분석 준비 중인 종목입니다'"*

2026-09-30 커밋 `563d542`에서 정확히 그렇게 만들었다
(`lib/widgets/common/data_unavailable_view.dart`):

| 상황 | 문구 | 액션 |
|---|---|---|
| `notReady` (404·빈 값) | **{티커} 데이터를 준비 중입니다** | 알려주기 + 이전 화면으로 |
| `offline` | 연결이 불안정합니다 | 다시 시도 |
| `serverError` | 일시적인 문제가 발생했습니다 | 다시 시도 + 알려주기 |

`TickerNotFoundException`(404)과 `notFound`가 `notReady`로 판정된다
(`kindOf`). **데이터 부재에는 "다시 시도"를 주지 않는다** — 눌러도 결과가
같아서 사용자가 헛되이 반복한다.

"오류"라는 단어를 쓰지 않는 것도 테스트로 못 박아 뒀다
(`test/data_unavailable_test.dart`).

→ **코드 변경 불필요.** 상장 40거래일 미만 종목이 그 화면으로 떨어진다.

## 10.5 이번에 바로 처리한 것 (서버 의존 없음)

### `?? 0.5` 폴백 제거

```dart
// before
if (latestData.aiSummary == null) { …fallback… }
final probability = latestData.aiProbability ?? 0.5;   // ← 없는 판단을 지어냄

// after
if (latestData.aiSummary == null || latestData.aiProbability == null) { …fallback… }
final probability = latestData.aiProbability!;
```

확률이 null인데 0.5로 메우면 **"AI 상승 확률 50%" + 상승 아이콘**
(`0.5 >= 0.5`)이 그려진다. 서버가 아무 판단도 주지 않았는데 앱이 중립
판정을 **지어내는** 것이다. `limited` 종목이 실제로 0.5를 보내므로
`data_quality`가 오기 전에도 이 수정만으로 절반은 막힌다.

> ⚠️ 다만 `limited`는 **null이 아니라 0.5를 명시적으로 보낸다.** 이 수정은
> "값이 없는 경우"만 막는다. `limited` 종목의 0.5를 거르려면 `data_quality`가
> 필요하다(S1).

### 검색 변형 질의 (⑤) — **반쪽만 가능하다**

`lib/utils/ticker_query.dart`. 원본으로 먼저 묻고 **빈 결과일 때만** 변형을
시도한다 — 서버가 이미 정규화를 한다면 추가 요청이 아예 안 나간다.

| 입력 | 시도 순서 |
|---|---|
| `BRK.B` | `BRK.B` → `BRK-B` → `BRKB` |
| `BRK-B` | `BRK-B` → `BRK.B` → `BRKB` |
| `BRKB` | `BRKB` **만** |
| `NVDA` | `NVDA` **만** |

**⚠️ 구분자 없는 `BRKB`는 앱이 못 푼다.** 처음엔 "끝 글자가 A·B·C면
클래스주"로 보는 휴리스틱을 썼다가 테스트가 `NVDA → NVD-A`,
`TSLA → TSL-A` 같은 쓰레기 질의를 잡아냈다. 4글자 일반 티커와 `BRKB` 같은
축약 표기는 **문자열만으로 구분할 수 없다.**

→ 구분자가 있을 때만 변형한다. **`BRKB` 케이스는 서버 정규화(S3)가
반드시 해야 한다.** 앱이 할 수 있는 건 여기까지다.

### 지수 수 하드코딩 금지 계약 (②)

`test/ticker_query_test.dart`가 지수 코드 등장 줄 ±3줄에 500/100/30/503/101이
**숫자로** 나오면 실패시킨다. `'S&P 500'` 같은 **라벨 문자열은 제외**한다 —
그건 개수 가정이 아니라 지수 이름이다.

### 전문가 코멘트 대체 체인 (⑦)

`expert_analysis` → `final_comment` → `summary`. 셋 다 null일 때만 숨긴다.

`expertAnalysisForLang`은 **언어별 필드**를 보므로, 한국어만 채워진 종목을
영어 사용자가 보면 null이 나온다. 이 대체 체인이 그 구멍도 같이 막는다 —
스펙이 요청한 것보다 넓게 고쳤다.

## 10.6 파이프라인 회신 반영 (2026-10-02)

맥미니 회신으로 S4·S5가 닫혔고, S1~S3은 서버(hypehere FastAPI) 담당으로
넘어갔다. 회신 내용에 따라 앱에서 3건을 추가 처리했다.

### 1. 빈 문자열을 null처럼 다룬다 (S5)

회신: *"이론상 summary와 ai_comment가 모두 비면 `final_comment`가 빈
문자열이 될 수 있다."* `??`는 빈 문자열을 거르지 못한다. 대체 체인의 각
단계에서 `trim().isEmpty`를 null로 본다.

### 2. 팩 문자열 해제 — **내가 만든 버그였다**

`aiFinalComment`·`aiSummary`는 `ko|||en|||zh|||ja|||es` 팩 문자열인데,
전날 넣은 `_expertText`가 **해제 없이 반환**하고 있었다. 대체 경로를 타면
구분자가 그대로 화면에 나왔다. `localize(lang)`를 체인 안으로 넣었다.

회신의 언어 대체 순서(`해당 언어 → ko`)는 기존 `localizePacked`가 이미
`해당 언어 → en → ko`로 처리하고 있어 추가 작업이 없었다.

### 3. `limited` 임시 판별 — **권장받지 않았지만 넣었다**

회신은 접두사 매칭을 *"권장하지 않는 임시 방편"*이라 했다. 그럼에도 쓴
이유는, 지금 FDXF·HONA·SPCX가 **"AI 상승 확률 50% + 상승"** 으로 보이기
때문이다. 서버가 판단을 포기한 자리에 앱이 중립 판정을 지어내고 있다.
틀린 숫자를 몇 주 더 보여주는 것보다 문자열 매칭의 위험이 작다고 봤다.

안전 설계 두 가지:
- **숨기는 방향으로만** 쓴다. 오탐은 "AI 블록 미표시"가 최악이고 미탐은
  현상 유지다. 반대로 쓰면 오탐이 곧 거짓 정보가 된다.
- 회신이 제시한 두 신호 중 **접두사만** 쓴다. `probability_multi == null`은
  과거 single-head 모델 행에서도 null이라 오탐이 크다고 회신에 적혀 있다.

`data_quality`가 조회 API에 나오면 `lib/utils/limited_analysis.dart`를
**통째로 지우고** `analysis_mode == 'limited'`로 교체한다.

### 되짚을 만한 판단 다섯

**① 확률값으로는 유효성을 판단할 수 없다.** `limited`는 `probability`를
0.5로 **채워서** 보내고, 정상 종목의 확률이 정확히 0.5일 수도 있다.
근거는 `ai_available`이어야 한다. 테스트에 두 케이스를 다 박았다.

**② NULL 환산은 서버에서 한 곳에만.** `app/utils/data_quality.py`.
읽기 경로가 늘어도 규칙이 갈라지지 않게 하려는 것이고, 백필 없이
215,314행을 그대로 뒀다.

**③ stale 임계값은 1이 아니라 2거래일.** 종목별 날짜 차이는 정상이고,
1에서 켜면 부분 적재일마다 정상 종목이 빨개진다. 늑대 소년이 된 배지는
무시된다. 단위도 달력일이 아니라 거래일이다 — 아니면 주말마다 뜬다.

**④ 표기 변경(`BRKB → BRK-B`)은 사용자에게 알리지 않는다.** 같은 회사의
같은 주식이다. 심볼은 서버 표기를 따르되 조용히 간다.

**⑤ 목록 엔드포인트에 `data_quality`를 안 넣었다.** `/scores/top`·
`/market/*`는 `ai_probability`를 안 내려줘서 **거짓 AI 숫자가 생길 자리가
없다.** 네 군데 쿼리와 응답 스키마를 바꾸는 비용에 비해 지금 얻는 게
없다. S2 확장 때 함께 넣는다.

### 밟은 함정 셋 (같은 데서 또 막히지 않게)

1. **psql이 `DATABASE_ANALYTICS_URL`을 못 읽는다** — `options=` 쿼리
   파라미터의 `=`를 URI 파서가 거부한다. SQLAlchemy 엔진으로 간다.
2. **`/tmp` 스크립트는 `cd`만으로 `app`을 못 찾는다** — `sys.path[0]`이
   `/tmp`다. `PYTHONPATH`를 명시한다.
3. **pydantic `field_validator`는 선언 순서상 앞선 필드만 본다** —
   `new_ticker`에 건 검사가 `reason`을 못 봐서 조용히 통과했다.
   교차 필드 검사는 `model_validator(mode="after")`여야 한다.
   엔드포인트 테스트의 422 케이스가 잡았다.

### 남은 것

- **stale 배지 UI** — 모델(`Freshness`)까지 붙였고 화면만 남았다.
- 보유·관심종목 **자동 이관** — 지금은 종목 상세에서만 안내한다.
  사용자 데이터를 쓰는 작업이라 영향 사용자 0명인 지금 서두르지 않는다.
