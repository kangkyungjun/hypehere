## A1. 스토어 name·subtitle — 커뮤니티 제거

### 실측 결과 — 앞선 보고(10파일)는 **과소 집계였다**

grep 패턴이 zh-Hant의 `社群`과 es의 `Foro`(포럼)를 놓쳤다.
**실제 14파일**이고 **10개 로케일 전부**가 subtitle에 걸려 있다.

| 파일 | 현재 | 제안 | 자수 |
|---|---|---|--:|

| `ja/name.txt` | MarketLens: AI米国株分析**&コミュニティ** | MarketLens: AI米国株分析 | 19 |
| `zh-Hans/name.txt` | MarketLens: AI美股分析**与投资社区** | MarketLens: AI美股分析 | 18 |
| `zh-Hant/name.txt` | MarketLens：AI美股分析**與投資社群** | MarketLens：AI美股分析 | 17 |

구분자를 쉼표/y로 바꿔 30자에 맞췄다.

**대체어 선정 근거**: 커뮤니티 자리에 **실제로 있는 기능**을 넣는다.
보유종목 관리(Holdings/保有管理/持仓管理/持股管理/Cartera)는 탭으로 존재하며,
1.10.0 description에서 이미 같은 이유로 커뮤니티를 대체한 기능이다. 일관된다.

### 검증
```bash
# 커뮤니티 관련어 전수 (社群·Foro 포함한 넓은 패턴)

# 자수 제한 (name·subtitle 각 30자)
for f in fastlane/metadata/*/name.txt fastlane/metadata/*/subtitle.txt; do
  n=$(python3 -c "print(len(open('$f').read().strip()))")
  [ "$n" -gt 30 ] && echo "OVER $f ($n)"
done
```

- **낮음.** 메타데이터만이라 코드 회귀 없음.
- 단, **앱 이름 변경은 App Store 심사 대상**이다. 1.10.0 제출 시 함께 나간다.
- ASO 영향: "커뮤니티/community" 키워드를 잃는다. 어차피 없는 기능이므로 손실이 아니라 **오탐 유입 제거**다.

## B1. 게스트 관심종목 승계 (데이터 유실 진행 중)

### 문제 구조 (실측)

`marketlens_watchlist_guest` / `marketlens_portfolio_guest`로 **저장은 되는데
읽는 경로가 없다.** 키 생성 함수 밖 소비처 **0곳**.

| 경로 | 코드 | 현재 동작 |
|---|---|---|
| 앱 재시작 | `watchlist_provider.dart:57-71` | `lastUserId == null` → 레거시 `marketlens_watchlist`만 읽음. **게스트 키 미조회** |
| 가입/로그인 | `:135-141`, `:148-153` | 유저 키 → 없으면 **레거시 키** 폴백. **게스트 키 미조회** |
| 전환 시 저장 | `:106` | `_currentUserId != null` 조건 → **게스트에서 나갈 때 저장 안 함** |

`portfolio_provider.dart:142-160`도 같은 게스트 키를 만들지만 역시 읽기만 하고
승계 경로가 없다.

### 수정 방침

**두 지점에 게스트 키 폴백을 추가한다. 레거시 폴백과 같은 자리, 같은 패턴.**

1. **`initialize()`** — `lastUserId == null`일 때 레거시 키 **다음으로** 게스트 키를 읽는다.
   (게스트 키가 있으면 그것을 우선한다 — 더 최근 데이터이므로)
2. **`switchUser(userId != null)`** — 유저 키가 비었을 때
   레거시 폴백 **앞에** 게스트 키를 확인하고, 승계 후 게스트 키를 **삭제**한다.
3. **`switchUser`의 저장 조건**(`:106`)에서 `_currentUserId != null`을 제거해
   게스트 상태의 메모리 목록도 전환 직전에 디스크로 내린다.

**병합 정책**: 유저 키에 이미 데이터가 있으면 **덮어쓰지 않는다.**
서버 동기화본이 정본이므로 게스트 데이터는 버린다(로그만 남김).
비어 있을 때만 승계한다 — 이것이 실제 피해 시나리오의 100%다.

### 검증 — 테스트를 반드시 먼저 쓴다

`test/watchlist_guest_migration_test.dart` 신규:

| # | 시나리오 | 기대 |
|---|---|---|
| 1 | 게스트로 3종목 담기 → `initialize()` 재실행 | 3종목 유지 |
| 2 | 게스트로 3종목 → `switchUser(42)` | 유저 42가 3종목 승계, 게스트 키 삭제됨 |
| 3 | 유저 42에 이미 5종목 → 게스트 3종목 상태에서 `switchUser(42)` | 유저 5종목 유지(덮어쓰지 않음) |
| 4 | 레거시 키와 게스트 키가 동시 존재 | 게스트 우선 |
| 5 | 게스트 보유종목(portfolio)도 동일하게 승계 | 승계됨 |
| 6 | `switchUser(null)` (로그아웃) | 유저 데이터 저장 후 비움, 게스트 키 오염 없음 |

**수동 확인**: 시뮬레이터에서 비로그인 → 종목 담기 → 앱 강제종료 → 재실행 →
목록 유지 확인 → 가입 → 목록 유지 확인.

### 위험
- **중간.** SharedPreferences 마이그레이션은 되돌리기 어렵다.
- 완화: 승계는 **복사 후 삭제**이고, 유저 키가 비었을 때만 동작하므로
  기존 로그인 사용자에게는 코드 경로가 닿지 않는다.
- 테스트 6종을 선행 작성한다.

## B2. 온보딩 건너뛰기의 가짜 프로필 제거

`_skipAndClose`(`investment_profile_onboarding_screen.dart:138-148`)가
`InvestmentProfile.defaultProfile()`을 저장한다. 서버가 이후
`has_investment_profile: true`를 반환해 **다시 묻지 않는다.**

### 수정
- `_skipAndClose`에서 `saveProfile` 호출을 **제거**하고 그냥 닫는다.
- 프로필 미설정 사용자에게 **프로필 화면에서 설정 진입점**을 노출한다
  (이미 있는지 확인 후, 없으면 추가).

### 위험
- **낮음.** 다만 `has_investment_profile: false`인 사용자가 생기므로,
  이 값을 참조하는 곳이 null-safe한지 확인 필요.
- 이미 저장된 가짜 프로필은 **소급 삭제하지 않는다** — 진짜 "균형형" 사용자와
  구별할 방법이 없다. 신규 사용자부터 적용.

## C1. 매매 단정 표현 중립화 (1.10.1)

### 실측 — 건드릴 것과 건드리면 안 되는 것

⚠️ **중요**: ko ARB에 `매수/매도`가 들어간 문자열이 30개 넘게 있지만
**대부분은 손대면 안 된다.** `매도일`·`매도 수량`·`총 매수금액`은
사용자 본인의 거래 기록 라벨이지 조언이 아니다.

**✅ 이미 중립화된 것 (건드리지 말 것)**
`scoreStrongBuy`~`scoreStrongSell` — 5개 언어 전부
(강력긍정/Strong Positive/強いポジティブ/强烈正面/Muy Positivo).
서버가 보내는 `'매수권고'`·`'적극매수'`도 이 키로 매핑되므로
(`holding_list_item.dart:40-43` 외 2파일) **이 경로는 이미 깨끗하다.**

**🔴 수정 대상 — 10키 × 5언어 = 50문자열**

| 키 | 현재(ko) | 성격 |
|---|---|---|
| `aiScoreSubtitle` | AI 점수 (0: **매도 신호** ~ 100: **매수 신호**) | **상시 노출** |
| `aiSignalStrongBuyDesc` | **강력 매수** (80-100)… | 다이얼로그 |
| `aiSignalBuyDesc` | **매수** (60-79)… | 다이얼로그 |
| `aiSignalHoldDesc` | **보유** (40-59)… | 다이얼로그 |
| `aiSignalSellDesc` | **매도** (20-39)… | 다이얼로그 |
| `aiSignalStrongSellDesc` | **강력 매도** (0-19)… | 다이얼로그 |
| `coachMarkTickerScore` | …**70 이상은 매수 신호입니다** | **단정형·코치마크** |
| `recBuyRecommend` | 보유 확대 (**추가매수 추천**) | 포트폴리오 조언 |
| `recSellRecommend` | 보유 축소 (**매도 추천**) | 포트폴리오 조언 |
| `recommendedAction` | **권고 사항** | 섹션 라벨 |

**중립화 방향**: 이미 확립된 `scoreXxx`의 어휘(긍정/중립/부정)로 통일한다.
새 어휘를 만들지 않는다.
- `aiScoreSubtitle` → "AI 점수 (0: 부정 ~ 100: 긍정)"
- `aiSignalStrongBuyDesc` → "강력긍정 (80-100): 기술적·재무적 지표가 모두 강한 긍정 신호"
- `coachMarkTickerScore` → "AI 점수 추이를 확인하세요" (단정 부분 삭제)
- `recBuyRecommend` → "비중 확대 검토" / `recSellRecommend` → "비중 축소 검토"
- `recommendedAction` → "참고 정보"

**⚠️ 서버 자유 텍스트 문제 (별건)**
`holding_detail_sheet.dart:166`의 `recommendedAction` **값**은 서버가 내려주는
자유 텍스트를 그대로 렌더링한다 — 앱이 내용을 통제하지 못한다.
FastAPI 코드가 이 저장소 밖이라 **서버 측 문구 점검이 별도로 필요**하다.

**🟡 판단 보류 — 애널리스트 컨센서스**
`ratingBuy`/`ratingStrongBuy`/`ratingSell`/`ratingStrongSell`은
`ticker_detail_helpers.dart` 한 파일에서만 8곳 쓰인다.
이건 **제3자 애널리스트의 평가를 보도하는 것**이라 앱 자신의 조언과 성격이 다르다.
→ 문구는 유지하되 **"출처: 애널리스트 컨센서스" 귀속 표시를 붙이는 쪽**을 권한다.

### 검증
```bash
flutter gen-l10n && flutter test test/l10n_coverage_test.dart
```
기존 l10n 커버리지 테스트가 키 집합 동일성과 번역 누락을 잡아준다.

### 위험
- **번역 품질.** 50개 문자열을 5개 언어로 고쳐야 하고, ja/zh/es는 검수가 어렵다.
- 완화: 어휘를 `scoreXxx`가 **이미 5개 언어로 확정한 것**에서만 가져온다.
  새 단어를 만들지 않으므로 번역 리스크가 최소화된다.

## C2. 면책 문구 확대 (1.10.1)

### 현황
앱 전체에서 면책은 **`ai_chat_screen.dart` 한 곳**뿐이고,
그마저 **하루 1회·회색 말풍선·스크롤하면 사라진다**.
AI 점수 화면·티커 상세·목표가·관심종목 AI 의견·포트폴리오 AI 카드·
거시지표 AI 설명 — **전부 0건**. 온보딩도 0건.

### 수정 방침
1. 공용 위젯 `MlDisclaimerNote` 신설 — `caption`(11px) 1~2줄, 기존 토큰만 사용
2. AI 판단이 표시되는 **모든 섹션 하단**에 배치
3. 문구에 반드시 포함: **① 정식 금융투자업자가 아님 ② 개별 상담·자금운용 불가
   ③ 원금 손실 가능성과 그 손실이 투자자에게 귀속됨**
4. 스토어 description의 기존 5개 면책 조항을 **앱 안으로** 옮긴다

### 위험
- **밀도.** 여백 타이트 선호와 충돌할 수 있다.
- 완화: `caption` 크기 + 섹션당 1회 + 접이식 없이 정적 1줄.
  화면당 최대 1개 원칙(같은 화면에 AI 섹션이 여럿이면 화면 하단에 1개).

## D1. 익명 계측 (1.11.0)

### 현황
```dart
// activity_service.dart:38-39
final token = await _auth.getAccessToken();
if (token == null || token.isEmpty) return;  // 비로그인 → 집계 대상 아님
```
호출부는 `main.dart:664`(앱 시작), `:671`(포그라운드 복귀) 2곳.
이벤트 SDK 0건, `logEvent` 0건.

### 수정 방침
1. 설치 시 익명 `device_id`(UUID) 발급 → SharedPreferences 저장
2. `maybePing()`의 로그인 조건 제거, `device_id` + `is_logged_in` 전송
3. 로그인 시 `device_id` ↔ `user_id` **머지** (서버)
4. 모든 이벤트에 공통 속성: `is_logged_in`, `market_session`, `local_date`, `platform`

### 선행 필요
- **서버 스키마 변경** — `activity/ping`이 익명 요청을 받아야 하고,
  `device_id` 컬럼과 머지 로직이 필요하다. FastAPI/Django 양쪽 확인 필요.
- **`ios/Runner/PrivacyInfo.xcprivacy` 부재** — 확인 완료.
  익명 식별자를 수집하면 Apple의 privacy manifest 요구사항을 재검토해야 한다.
- App Store Connect의 **App Privacy 답변 갱신** 필요 (2.3.1 연계)

### 위험
- **높음(범위).** 앱만으로 끝나지 않는다. 서버·심사 메타데이터가 함께 움직인다.
- 그래서 별도 릴리스로 분리했다.

## E1. AI 쿼터 일일 리셋 (1.10.1)

### 현황 (실측)
```dart
// chat_provider.dart:44-54
/// 무료 메시지 절대 한도(10). 자정 리셋 없음 — 누적 차감.
static const int freeLimit = 10;
int _quotaUsed = 0;
static const _kQuotaUsed = 'chat_quota_used';
int get quotaRemaining => (freeLimit - _quotaUsed).clamp(0, freeLimit);
```
조작 지점은 `:296`(로드) `:304`(차감) `:311-312`(광고 보너스) 3곳뿐.

### 수정 방침
`_kQuotaDate` 키를 추가하고, 로드 시 저장된 날짜가 오늘이 아니면
`_quotaUsed = 0`으로 리셋한다. 날짜 계산은 **앱에 이미 있는 선례**를 쓴다
(`watchlist_screen.dart:69-93`의 `_todayYmd()`).

**`freeLimit`은 10 그대로 두고 일일 리셋만 추가할 것을 권한다.**

근거: 사용자 규모가 작은 지금은 **광고 매출보다 리텐션이 압도적으로 중요**하다.
게다가 현재 광고 게이트는 로드 실패 시에도 +5를 주는 fail-open이라
(`ai_chat_screen.dart:186-191`) **지금도 벽 역할을 제대로 못 한다.**
상수 하나이므로 나중에 얼마든지 조일 수 있다.

### 검증
- 단위 테스트: 어제 날짜로 저장된 상태 → 로드 시 0으로 리셋
- 같은 날 재로드 시 리셋되지 않음
- 광고 보너스가 리셋과 충돌하지 않음(`_quotaUsed` 음수 방지는 이미 `clamp`)

### 위험
- **낮음.** 되돌리기가 상수 하나 + 조건 하나.
- 광고 노출 감소는 감수. 단 **D1 계측 전이라 효과를 측정할 수 없다** —
  이건 "측정 없이 넣는" 예외로 두고, 근거는 위 논증으로 갈음한다.

## 실행 순서

```
1.10.0  (제출 전, 재빌드 필요 — 빌드번호 +43)
  ├─ A1  스토어 메타데이터 14파일          [메타데이터만, 재빌드 불필요]
  ├─ B1  게스트 관심종목 승계 + 테스트 6종  [코드]
  └─ B2  온보딩 가짜 프로필 제거           [코드]
        ↓ 검증: flutter test 전체 + 시뮬레이터 수동 시나리오
        ↓ 재아카이브 → 배포 인증서 확보 후 제출

1.10.1
  ├─ E1  AI 쿼터 일일 리셋                [~20줄]
  ├─ C1  매매 표현 중립화 (10키 × 5언어)   [번역 검수 필요]
  └─ C2  면책 위젯 + 배치                 [신규 위젯]

1.11.0
  └─ D1  익명 계측                        [앱 + 서버 + 심사 메타데이터]
        ↑ 서버 스키마·PrivacyInfo.xcprivacy·App Privacy 답변 선행
```

### 왜 이 순서인가
1. **A1이 최우선인 이유**: 유일하게 **제출을 막는** 항목이다.
   없는 기능을 앱 이름에 광고하는 것은 App Store 2.3.1 정면 위반이다.
2. **B1이 1.10.0에 들어가는 이유**: 지금 이 순간에도 게스트 사용자가
   데이터를 잃고 있다. 수정 범위가 2파일로 좁고 테스트로 못 박을 수 있다.
3. **C1·C2를 미루는 이유**: 50개 문자열의 다국어 검수가 필요하고,
   1.10.0의 UI 개편 회귀 위험과 섞이면 원인 분리가 어렵다.
4. **D1이 마지막인 이유**: 앱만으로 끝나지 않는다. 서버 스키마와
   심사 메타데이터가 함께 움직여야 한다.
